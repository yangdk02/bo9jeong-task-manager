# 보구정 과업 관리 도구 개발 인수인계

## 1. 문서 목적

`261019_업프로젝트 1`에서 진행한 기획·설계 결과를 `bo9jeong` 개발 프로젝트로 전달한다. 이 문서는 개발 범위와 결정사항의 기준이며, 회의 기록이나 전체 대화 내용을 옮긴 문서가 아니다.

## 2. 제품 목표

발주처와 실무자가 프로젝트별 과업을 등록하고, 담당자가 수행한 최소 작업 단위와 여러 장의 증빙 이미지를 관리하며, 완료 실적을 바탕으로 보고서를 즉시 생성할 수 있는 `보구정 과업 관리 도구` MVP 웹 앱을 만든다.

현재 단계에서는 로컬 실행과 Vercel 기반 검증 배포를 함께 지원한다.

## 3. 확정된 기술 방향

- 웹 프론트엔드는 Streamlit을 사용하지 않는다.
- 구체적인 프레임워크는 개발 시작 시 현재 저장소 상황을 보고 선택한다.
- 로컬 개발에서는 구조화 데이터를 `data/local`의 CSV 파일 10개에 저장한다.
- 로컬 업로드 파일과 생성 보고서는 `storage` 아래 폴더에 저장한다.
- Vercel 검증 배포에서는 같은 10개 스키마를 Supabase Postgres에 저장하고 파일은 비공개 Supabase Storage에 저장한다.
- Google Sheets와 Google Drive는 구현하지 않는다.
- Vercel Hobby 배포는 시연·검증용으로 한정하며 실제 운영 전에 플랜 적합성을 다시 검토한다.
- 화면과 저장소를 분리해 이후 CSV 저장소를 다른 시스템으로 교체할 수 있게 한다.

## 4. 자료별 우선순위

1. 사용자의 최신 명시적 결정
2. 이 문서
3. `docs/DATA_SCHEMA.md`
4. `mockup/mockup.html`
5. 보구정 Notion과 기획 Slides·Sheets

목업에 존재하지만 이 문서에서 제외한 필드는 구현하지 않는다.

## 5. 핵심 개념

### 프로젝트

발주처, 계약 기간과 여러 과업을 묶는 최상위 단위다.

### 과업

프로젝트에서 계약한 업무 항목이다. 프로젝트 생성 시 체크리스트로 선택하며 목표 수량과 단위를 직접 입력한다.

예: 블로그 포스팅 5건, 카드뉴스 10장, 촬영 3곳.

### 작업

과업 아래에서 담당자가 등록하는 최소 실적 단위다. 상태가 `completed`인 작업 1행을 실적 1건으로 계산한다.

블로그 포스팅 과업의 목표가 5건이면 담당자는 실제 포스팅마다 작업을 1건씩 등록한다. 작업 한 건에 캡처본을 여러 장 첨부해도 실적은 1건이다.

일회성 과업은 생성 월에만 표시하고 다음 월로 이월하지 않는다. 월간 반복과 일회성 모두 선택한 달에 완료된 작업만 해당 월 실적으로 집계한다.

### 담당자

이름과 부서를 함께 관리한다. 프로젝트·과업·작업에는 각각 여러 담당자를 지정할 수 있다. 이름과 부서 양쪽 기준으로 조회할 수 있어야 한다.

현재 조직의 부서는 `경영관리`, `총무`, `기획`, `영상촬영`, `디자인`, `마케팅` 6개이며 샘플 담당자는 각 부서에 고르게 배치한다.

### 자료 DB

프로젝트별 로고, 로고 배치 가이드, 브랜드 가이드, 패키지 시안과 각종 제작물을 로컬에 저장하고 검색하는 기능이다.

## 6. MVP 화면 범위

### 필수

1. 웰컴 또는 홈
   - `안녕하세요, ___ 님!` 형태의 현재 담당자 선택
   - 상단에서도 현재 담당자 변경
2. 대시보드
   - 이번 달 전체·완료·남은 과업 수
   - 목표 작업 수를 채운 과업을 완료 과업 1개로 계산한 과업 기준 진행률
   - 최근 작업
3. 프로젝트 목록
   - 업체명 검색
   - 상태 필터
4. 프로젝트 등록
   - 기본 정보
   - 복수 담당자
   - 과업 체크리스트
   - 과업별 목표 수량·단위·담당자
5. 프로젝트 상세
   - 과업 현황
   - 담당자와 부서 필터
6. 과업 상세
   - 목표·완료·잔여 수량
   - 작업 목록
7. 작업 등록·상세
   - 날짜, 제목, 결과 URL, 메모, 상태, 복수 담당자
   - 여러 장의 캡처본·증빙 파일
   - 작업 등록 시 첨부 파일을 프로젝트 자료로도 함께 등록하는 선택 기능
   - 댓글·활동 기록
8. 자료 검색
   - 프로젝트, 자료명, 자료 유형, 담당자, 부서 기준 검색
   - 자료 등록·상세·파일 열기
9. 보고서 생성
   - 프로젝트와 기간 선택
   - 필요한 코멘트 입력
   - CSV와 로컬 파일을 읽어 첨부된 보구정 결과 보고 양식 기반의 편집 가능한 PPTX 1종으로 즉시 생성

### 현재 제외 또는 보류

- 목업의 `블로그 계정`·`공식/비공식` 입력
- 네이버 플레이스 수치 비교 화면과 관련 데이터
- 실제 로그인과 권한별 화면
- 별도 팀 관리 화면
- 보고서 이력 관리
- Google 연동 설정 화면
- 로그인과 접근 제한

## 7. 핵심 테이블

| 구분 | 테이블 | 한글명 | 목적 |
|---|---|---|---|
| 핵심 | `projects` | 프로젝트 | 발주처·계약 기간·상태 관리 |
| 핵심 | `tasks` | 과업 | 프로젝트별 목표 수량·단위 관리 |
| 핵심 | `works` | 작업 | 완료 실적의 최소 단위 관리 |
| 핵심 | `work_files` | 작업 파일 | 작업별 여러 증빙 파일 연결 |
| 보조 | `people` | 담당자 | 이름·부서와 현재 담당자 선택 |
| 보조 | `project_assignees` | 프로젝트 담당자 | 프로젝트 복수 담당자 연결 |
| 보조 | `task_assignees` | 과업 담당자 | 과업 복수 담당자 연결 |
| 보조 | `work_assignees` | 작업 담당자 | 작업 복수 담당자 연결 |
| 보조 | `assets` | 자료 DB | 마케팅 자료 파일 검색·조회 |
| 보조 | `comments` | 댓글·활동 기록 | 작업·자료 상세의 소통 이력 |

컬럼과 허용값은 `docs/DATA_SCHEMA.md`를 따른다.

## 8. 주요 데이터 관계

```text
projects → tasks → works → work_files
    │         │        │
    └ project_assignees
              └ task_assignees
                       └ work_assignees

people ← 각 *_assignees
projects → assets
works 또는 assets → comments
```

## 9. 상태와 선택 항목

- 프로젝트: `planned`, `active`, `completed`
- 과업: `planned`, `active`, `completed`
- 작업: `draft`, `completed`
- 자료: `planned`, `active`, `completed`
- 과업 범위: `SNS`, `블로그`, `디자인`, `촬영`, `영상`, `네이버 플레이스`, `광고`, `기타`
- 목표 단위: `건`, `장`, `곳`, `회`, `기타`
- 과업 주기: `monthly`, `once`

## 10. 목업과 최종 결정의 차이

| 목업 표현 | 개발 기준 |
|---|---|
| 사용자 | 담당자 |

## 12. 개발 시작 시 미결정 사항

아래 항목은 구현 전 결정하거나 안전한 기본값으로 제안해야 한다.

- 프론트엔드 프레임워크와 로컬 실행 명령
- CSV 동시 수정 방지 방식
- 초기 담당자 목록

미결정 사항이 있어도 저장소 골격과 읽기 전용 화면 개발은 진행할 수 있다. 사용자 데이터나 배포 방식에 영향을 주는 결정은 임의로 확정하지 않는다.

확정된 보고서·파일 기준:

- 보고서는 편집 가능한 PPTX 1종만 생성한다.
- 제공된 결과 보고 양식의 6개 기존 페이지는 표지, 블로그, SNS, 출사 사진, 출사 영상, 네이버 플레이스·코멘트 화면의 디자인 참고 자료로 사용한다.
- 생성 결과의 페이지 수는 고정하지 않고 선택한 기간과 포함되는 실적에 따라 필요한 만큼 구성한다.
- 앱 자체 업로드 용량 제한은 두지 않는다.
- 작업 증빙과 자료 DB에는 일반적으로 사용하는 이미지, 문서, 디자인 원본, 압축 파일과 영상 형식을 허용한다.
- 전체 CSV 샘플 데이터 생성은 사용자의 후속 요청에서 진행한다.

## 13. 삭제와 활동 기록

- 작업 수정 기능을 구현한다.
- 작업 삭제 시 `works` 행과 연결된 `work_assignees`, `work_files`, 작업 대상 `comments`를 함께 삭제하고 실제 작업 파일도 삭제한다.
- MVP에서는 삭제 백업과 휴지통을 구현하지 않는다. 백업 기능은 후속 범위다.
- 자동 활동 기록은 작업·자료의 생성, 수정, 상태 변경, 담당자 변경, 파일 추가·삭제 시 남긴다.
- 자료 담당자는 현재 스키마대로 1명만 지정한다.

## 14. MVP 완료 기준

- 담당자를 선택하고 프로젝트를 생성할 수 있다.
- 과업을 체크리스트로 선택하고 목표 수량·단위·담당자를 저장할 수 있다.
- 과업 아래에 작업을 등록하고 여러 증빙 파일을 첨부할 수 있다.
- 대시보드는 목표 작업 수를 채운 과업 수를 전체 과업 수와 비교해 진행률을 계산한다.
- 프로젝트·과업 상세에서는 완료 작업 수가 목표 수량과 초과 수행 여부에 정확히 반영된다.
- 이름과 부서로 프로젝트·과업·작업·자료를 조회할 수 있다.
- 로컬 자료 파일을 등록하고 유형별로 검색할 수 있다.
- 작업 및 자료에 담당자 댓글과 자동 활동 기록을 남길 수 있다.
- CSV 또는 업로드 파일이 없는 빈 상태에서도 앱이 오류 없이 실행된다.
- 앱을 다시 실행해도 로컬 CSV와 파일이 유지된다.
- 보고서를 요청 시 생성할 수 있고 보고서용 DB 테이블을 만들지 않는다.
